# PRD: NagaDo — "오늘 나가도 되나?"

> **NagaDo** = "나가도?"의 로마자 표기. 사용자가 매일 아침 던지는 질문 "지금 나가도 될까?"에 서비스가 대신 답한다는 서비스 정체성을 이름에 담았다.

## 1. 개요 (Overview)

### 1.1 한 줄 정의
**NagaDo**는 매일 아침 지정 시간에 **날씨 · 미세먼지 · 대중교통 도착 정보**를 하나의 카카오톡 메시지로 요약해 보내주는 개인화 브리핑 서비스다.

### 1.2 배경 / 문제 정의
- 출근 전 확인해야 할 정보가 **날씨 앱, 미세먼지 앱, 지하철 앱** 등 최소 3개 앱에 분산되어 있다.
- 앱을 여는 행위 자체가 반복적이고, 매일 아침 평균 2~3분을 소모한다.
- 확인을 깜빡하면 우산을 안 챙기거나, 미세먼지 나쁨인 날 마스크 없이 나가는 등 실질적 불편이 발생한다.

### 1.3 해결 방안
사용자가 **아무 행동도 하지 않아도** 정보가 먼저 도착하게 만든다. Pull(앱 열기) → Push(메시지 수신) 전환이 핵심 가치.

## 2. 목표 및 성공 지표 (Goals & Metrics)

### 2.1 목표
1. 매일 아침 설정 시간 ±1분 이내에 브리핑 메시지 발송
2. 메시지 하나로 "우산 / 마스크 / 출발 타이밍" 3가지 의사결정 완결
3. 서버 비용 0원~월 1만 원 이내로 운영

### 2.2 성공 지표 (개인 프로젝트 기준)
| 지표 | 목표치 |
|---|---|
| 발송 성공률 | ≥ 99% (월 기준) |
| 발송 지연 | 평균 30초 이내 |
| API 장애 시 폴백 동작률 | 100% (일부 데이터 누락 시에도 발송) |
| 본인 실사용 | 30일 연속 사용 후에도 유용하다고 판단 |

### 2.3 비목표 (Non-Goals)
- 불특정 다수 대상 상용 서비스화 (MVP 단계에서는 본인 + 지인 소수)
- 네이티브 모바일 앱 개발
- 실시간 채팅형 인터랙션 (초기엔 단방향 발송만)

## 3. 사용자 (Target User & Persona)

**페르소나: 김직장 (29, 서울 거주, 지하철 통근)**
- 매일 오전 7:30 전후 집에서 출발, 2호선 이용
- 아침에 시간이 없어 앱 여러 개 확인이 귀찮음
- 카카오톡은 기상 직후 무조건 확인함

**핵심 시나리오**
> 오전 7:00, 카카오톡 알림이 울린다.
> "☔ 오후 비 (강수확률 70%) → 우산 챙기세요 / 😷 미세먼지 나쁨 (PM2.5 82) / 🚇 강남역 2호선 상행 4분 후, 다음 열차 9분 후"
> 김직장은 우산과 마스크를 챙기고, 4분 열차는 포기하고 9분 열차에 맞춰 출발한다.

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 MVP (Phase 1) — 필수

#### FR-1. 날씨 브리핑
- **데이터 소스**: 기상청 단기예보 조회서비스 (공공데이터포털)
- 오늘의 최저/최고 기온, 강수확률, 강수형태(비/눈)
- 강수확률 ≥ 50% 시 "우산 챙기세요" 액션 문구 자동 삽입

#### FR-2. 대기질 브리핑
- **데이터 소스**: 에어코리아 대기오염정보 API
- 사용자 지역(측정소 기준) PM10 / PM2.5 등급
- "나쁨" 이상일 때 마스크 권고 문구 삽입

#### FR-3. 대중교통 도착 정보
- **데이터 소스**: 서울시 지하철 실시간 도착정보 API (또는 버스 도착정보 API)
- 지정 역 · 지정 방향의 다음 열차 2대 도착 예정 시간
- 발송 시점 기준 실시간 조회 (캐시 금지)

#### FR-4. 메시지 발송
- **채널**: 카카오톡 "나에게 보내기" API (카카오 디벨로퍼스)
- 위 3개 정보를 하나의 텍스트 메시지로 조합
- 이모지 기반 시각적 구분 (☔ 😷 🚇)

#### FR-5. 스케줄링
- 사용자 지정 시각(기본 07:00, KST)에 매일 자동 실행
- 주말 발송 on/off 옵션

#### FR-6. 장애 폴백
- 특정 API 실패 시 해당 섹션만 "정보 조회 실패"로 표기하고 **나머지는 정상 발송**
- 3회 재시도(지수 백오프) 후 실패 처리

### 4.2 Phase 2 — 확장
| 기능 | 설명 | 데이터 소스 |
|---|---|---|
| 따릉이 판정 | 날씨+미세먼지 조합으로 "자전거 출근 가능" 여부 | 서울시 따릉이 API |
| 옷차림 추천 | 기온 구간별 복장 가이드 문구 | 자체 룰 기반 |
| 다중 사용자 | 지인 등록, 사용자별 지역/역/시간 설정 | DB 도입 |
| 웹 설정 페이지 | 출발역·발송시간·옵션을 웹에서 변경 | 자체 프론트 |

### 4.3 Phase 3 — 아이디어 백로그
- 카카오톡 채널(챗봇) 전환으로 양방향 질의 ("지금 나가면?")
- 캘린더 연동: 첫 일정 시간 기준 발송 시각 자동 조정
- 주유소 유가 정보(오피넷 API) — 차량 통근자 버전

## 6. 시스템 설계 (초안)

### 6.1 아키텍처
```
[스케줄러 (cron / GitHub Actions / EventBridge)]
        │  매일 07:00 KST 트리거
        ▼
[브리핑 파이프라인 (서버리스 함수 or 경량 서버)]
   ├─ ① 기상청 API 호출 ──┐
   ├─ ② 에어코리아 API 호출 ─┼─ 병렬 호출 (asyncio / Promise.all)
   ├─ ③ 지하철 API 호출 ──┘
   ├─ ④ 메시지 템플릿 렌더링
   └─ ⑤ 카카오 "나에게 보내기" 발송
        │
        ▼
[로그 저장 (파일/DB)] + [실패 시 관리자 알림]
```

### 6.2 기술 스택 후보
| 레이어 | 옵션 A (최소비용) | 옵션 B (학습형) |
|---|---|---|
| 실행 환경 | GitHub Actions cron | AWS Lambda + EventBridge |
| 언어 | Python (requests, httpx) | Node.js / Spring Boot |
| 저장소 | 없음(무상태) → 로그만 | SQLite → RDS |
| 시크릿 | GitHub Secrets | AWS Secrets Manager |

> MVP는 **옵션 A**로 시작 권장 — 서버 관리 0, 비용 0. Phase 2에서 다중 사용자 도입 시 옵션 B로 마이그레이션.

### 6.3 핵심 기술 이슈 (미리 알아둘 것)
1. **카카오 토큰 갱신**: 카카오 액세스 토큰은 만료됨 → 리프레시 토큰 자동 갱신 로직 필수. MVP 최대 난관 예상 지점.
2. **기상청 API 좌표계**: 위경도가 아닌 격자(X,Y) 좌표 사용 → 변환 로직 필요.
3. **에어코리아 측정소 매핑**: 주소 → 근접 측정소 조회 API를 한 단계 거쳐야 함.
4. **GitHub Actions cron 지연**: 정시 실행이 수 분 밀릴 수 있음 → 지연에 민감하면 옵션 B 고려.
